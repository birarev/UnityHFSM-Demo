# UnityHFSM.Demo

**Автор:** Бирюкова Арина

**Тема:** «Анализ и проектирование системы переходов и декораторов в библиотеке UnityHFSM»

**Исследуемая библиотека:** [UnityHFSM](https://github.com/Inspiaaa/UnityHFSM)

**Версия:** 2.3.0

**Коммит исходников:** `f8fdc2efb862522acd26fab6cd940886c84cde37`

**Технологии:** C#, .NET 10, UnityHFSM

Демонстрационный проект предназначен для исследования архитектуры переходов, применения паттерна Decorator и проверки порядка вызовов при смене состояний.

Приложение использует оригинальные исходники UnityHFSM без изменения их реализации.

## Цель демонстрации

Показать, как в UnityHFSM организованы проверка условий, смена состояний и расширение поведения переходов с помощью декораторов.

В рамках демонстрации исследуются:

- взаимодействие `StateMachine` и `TransitionBase`;
- проверка условий через `Transition.ShouldTransition()`;
- применение `DecoratedTransition` к существующим переходам;
- вызов дополнительных обработчиков до и после операций перехода;
- сохранение исходной логики при добавлении нового поведения.

## Архитектурное решение

В основе исследуемого механизма лежит общий тип `TransitionBase<TStateId>`, через который автомат взаимодействует с различными реализациями переходов.

`Transition<TStateId>` реализует обычный переход с условием, определяющим возможность смены состояния.

`DecoratedTransition<TStateId>` наследуется от `TransitionBase<TStateId>` и одновременно хранит ссылку на другой переход. Он делегирует ему выполнение основных операций, добавляя необязательные обработчики до и после вызовов.

`TransitionDecorator<TStateId>` используется для создания декорированных переходов с общим набором обработчиков.

Таким образом, паттерн **Decorator** позволяет расширять поведение существующих переходов без изменения их исходных классов и логики `StateMachine`.

## Демонстрационный сценарий

В приложении реализован конечный автомат с тремя состояниями:

```text
Idle ──────────→ Working ──────────→ Completed
     команда              выполнено
     запуска              2 единицы работы
```

**Idle — ожидание.** Автомат остаётся в исходном состоянии, пока `startRequested == false`. После получения команды запуска переходит в `Working`.

**Working — выполнение работы.** Автомат отслеживает количество выполненных единиц работы. Когда `workUnits >= 2`, происходит переход в `Completed`.

**Completed — завершение.** Конечное состояние, для которого в демонстрационном сценарии не зарегистрированы исходящие переходы.

Оба перехода создаются как обычные `Transition<string>`, после чего оборачиваются в `DecoratedTransition<string>` с помощью общего объекта `TransitionDecorator<string>`.

## Реализация Decorator

В проекте используются шесть обработчиков:

| Обработчик | Назначение |
|---|---|
| `beforeShouldTransition` | Действие до проверки условия |
| `afterShouldTransition` | Действие после проверки условия |
| `beforeOnTransition` | Действие до вызова `BeforeTransition` исходного перехода |
| `afterOnTransition` | Действие после `BeforeTransition` |
| `beforeAfterTransition` | Действие до вызова `AfterTransition` исходного перехода |
| `afterAfterTransition` | Действие после `AfterTransition` |

Библиотека поддерживает восемь необязательных обработчиков, включая `beforeOnEnter` и `afterOnEnter`. В данном сценарии эти два обработчика не используются.

Все действия логируются в консоль, что позволяет наблюдать реальный порядок вызовов.

### Порядок выполнения успешного перехода

```text
1. beforeShouldTransition
2. Transition.condition
3. afterShouldTransition
4. beforeOnTransition
5. Transition.onTransition
6. afterOnTransition
7. Выход из старого состояния
8. Вход в новое состояние
9. beforeAfterTransition
10. Transition.afterTransition
11. afterAfterTransition
12. FSM.StateChanged
```

При ложном условии смена состояния не происходит, но обработчики до и после проверки условия вызываются.

Обработчики декоратора не заменяют исходную проверку и не изменяют её возвращаемое значение.

## Проверка результата

Демонстрационный сценарий включает пять последовательных вызовов `StateMachine.OnLogic()`:

1. Ожидание команды — состояние `Idle`.
2. Получение команды запуска — переход в `Working`.
3. Выполнение одной единицы работы — состояние `Working`.
4. Выполнение второй единицы работы — переход в `Completed`.
5. Повторная проверка — состояние `Completed` сохраняется.

После каждого шага программа сравнивает фактическое состояние с ожидаемым. При несовпадении выбрасывается исключение.

Фрагмент вывода успешного перехода:

```text
11. Idle → Working: до выполнения перехода / BeforeTransition; активно: Idle
12. Idle → Working: оригинальный Transition.onTransition; активно: Idle
13. Idle → Working: после BeforeTransition (смена состояния ещё впереди); активно: Idle
14. Idle → Working: после смены состояния, до AfterTransition; активно: Working
15. Idle → Working: оригинальный Transition.afterTransition; активно: Working
16. Idle → Working: после выполнения перехода / AfterTransition; активно: Working
17. FSM.StateChanged: Working
```

Итоговое сообщение:

```text
38. Проверка сценария пройдена: Idle → Working → Completed.
```

В выполненной проверке с .NET SDK 10.0.100 проект собрался без ошибок и предупреждений и завершился с кодом 0.

## Архитектурные выводы

Практическая демонстрация подтверждает следующие особенности реализации:

- `StateMachine` работает с переходами через общий тип `TransitionBase<TStateId>`.
- `DecoratedTransition` добавляет дополнительные действия без изменения исходного `Transition`.
- Один `TransitionDecorator` может создавать несколько обёрток с одинаковой конфигурацией.
- Проверка условия выполняется исходным переходом, а декоратор сохраняет её результат.
- Обработчики до и после выполнения перехода вызываются в определённом порядке относительно смены активного состояния.

### Ограничения реализации

При анализе исходного кода также выявлены особенности:

- `forceInstantly` копируется при создании декоратора; последующие изменения этого поля во внутреннем переходе не отражаются автоматически в обёртке.
- Обработчики `ShouldTransition` получают объект внутреннего перехода, но не получают результат проверки отдельным параметром.
- `DecoratedTransition.Init()` не вызывает `Init()` внутреннего перехода. Это необходимо учитывать при создании пользовательских переходов и вложенных обёрток.
- В библиотеке отсутствует общий абстрактный класс декоратора для повторного использования логики делегирования.
